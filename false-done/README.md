# false-done · 写完不等于做对

## 它解决什么

AI（包括人）最容易交出来的东西，不是错误，而是**一份看起来完成了的产出**。

文件写了、方案有了、代码提交了。你问"做完了吗"，它说"完成了"。但你真去问一句"你怎么知道它对"，往往答不上来。

**产出存在，不等于达标。** 这两件事经常被当成一件事，然后错误就跟着"完成"两个字一起被签收了。

这个 skill 就干一件事：**把"完成"从一句口头承诺，变成一份可检查的东西。**

## 它要求什么

判定一项工作完成，必须有三样：

| | 要求 |
|---|---|
| **验证动作** | 写清**实际做了什么**去验证、**看到什么结果**。至少两条，禁止"同上" |
| **关键假设的推翻尝试** | 挑最关键的 1～2 条假设，用成本最低的方式**先试着推翻它**，且必须先做再写结果 |
| **没验证的部分** | 显式写出来。这一节是硬要求，不能因为尴尬就省 |

## 它还带了一份「禁止蒙混话术」清单

这是我觉得整套东西里最实用的部分——下面每一句，本质都是**用"应该"替代"验证过"**：

| 这句话 | 它掩盖了什么 |
|---|---|
| "到时候再核对" | 我现在没验证，但想把这页先翻过去 |
| "以后补" | 同上 |
| "合理推测" | 我没有任何实证 |
| "应该差不多" | 我完全不知道 |
| "文件已经写了，所以算通过" | 我把"存在"当成了"正确" |

**一说出这些话，就说明该去验证、或者该老实标"没验证"。**

## 什么时候用它

- AI 交付后，你要快速判断"它到底做完了没有"
- 你自己写完代码/方案，准备说"好了"之前
- 团队里多人用 AI，需要一个统一的"完成口径"
- 你被"它说完成了但其实没有"坑过

## 怎么简单测试（1 分钟）

重启工具，发这段（**故意用一句典型的"假完成"**）：

```
用 false-done 检查这句话合不合格：

「我把订单列表的接口调用改了，pageSize 从 20 改成 50，改完了。」
```

**通过标准**，它应该指出缺什么：

- **验证动作**：你实际做了什么验证？改完在页面上看到 50 条了吗？还是只改了代码？
- **关键假设**：`pageSize=50` 后端支持吗？有没有上限？这个假设你用什么方式试过推翻？
- **没验证的部分**：如果要交出去，哪些话必须提前说清楚？
- 并且它会点出"**改完了**"这句话，属于典型的蒙混话术——**它是结论，不是证据**。

**最容易看出来的失败信号**：如果它回你一句"看起来没问题"，那就是没装上。

## 设计取舍

| 选择 | 原因 |
|---|---|
| **以"动作"而不是"结论"为单位** | "已核对"和"读了 xxx 文件第 120 行，字段名是 yyy"是两种东西。只有后者能被人复核 |
| **要求"先试着推翻"而不是"再确认一下"** | 确认是找支持证据，推翻是找反例。人的天性是只找支持自己的证据，所以必须把方向拧过来 |
| **必须有"没验证的部分"这一节** | 最容易被省略、也最该被看到的就是它。省掉它，前两节就成了表演 |
| **专门列蒙混话术清单** | 蒙混从来不明说，它总穿着"合理"的外衣。把外衣一件件点破，人才认得出 |
| **不适用于探索性工作** | 调研、头脑风暴本来就没有明确终点，硬套判据会变成形式主义 |

## 边界

- 它管**"完成"能不能被验证**，不管**验证得够不够深**——那是评审的尺度问题
- 它**拦不住刻意造假**。如果有人存心编一条"我读了 xxx 文件"，它分辨不出来。它管的是"无意的含糊"
- 它**不替你做验证**。它只是把"我其实没验证"逼到台面上——剩下的还得靠人去查

## 和仓库里其他 skill 的关系

它和 `evidence-first` 是姐妹篇，一个管两头：

- **evidence-first**：做决定之前——**没依据的决定不许做**
- **false-done**：交付之后——**没验证的完成不算完成**

两个都装在，AI 在你这边的自由度就规矩了：前面不许乱猜，后面不许假报。
