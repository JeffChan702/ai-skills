# false-done — 写完不等于做对

## 它解决什么

AI（包括人）最容易交出来的东西，不是错误，而是**一份看起来完成了的产出**。

文件写了、方案有了、代码提交了。你问"做完了吗"，它说"完成了"。但你真去问一句"你怎么知道它对"，往往答不上来。

**产出存在，不等于达标。** 这两件事经常被当成一件事，然后错误就跟着"完成"两个字一起被签收了。

## 一条铁律

**"文件在"不是完成判据。**

判定一项工作完成，必须有一份**可检查的判据**——具体到"做了什么动作、看到了什么结果"，而不是"东西已经在那儿了"。

## 完成判据里必须有的三样

### 1. 验证动作（不是结论，是动作）

写清**你实际执行了什么**去验证，以及**结果是什么**。至少两条。

| 差的写法 | 好的写法 |
|---|---|
| "已核对接口字段" | "读了 `service/order.js` 第 120-140 行，确认字段名是 `totalAmount`；用列表接口返回的 JSON 断言过该字段存在" |
| "同上" | （禁止——每条都要单独写） |
| "确认无影响" | "删掉新分支后跑了一遍旧路径，输出与改动前一致" |

**禁止空列表，禁止"同上"。** 没执行过就写"未执行"，不要含糊过去。

### 2. 最关键的假设，先试着推翻它

任何方案都建立在几条关键假设上（"这个字段后端一定返回""这条路径只有这里会走"）。

做法是：**挑出最关键的 1～2 条，用成本最低的方式先试着推翻它们**——而不是等实现完了再看对不对。

而且必须**先做，再写结果**。写了动作却没写结果，等于没做。

结果只有三种，如实写：**成立 / 被推翻 / 卡住无法验证**。

### 3. 禁止用来蒙混过关的话术

以下每一句，都是**用"应该"替代"验证过"**：

| 这句话 | 它掩盖了什么 |
|---|---|
| "到时候再核对" | 我现在没验证，但我想先把这页翻过去 |
| "以后补" | 同上 |
| "合理推测" | 我没有任何实证 |
| "应该差不多" | 我完全不知道 |
| "文件已经写了，所以算通过" | 我把"存在"当成了"正确" |

**看到自己想说这些话，就是该去验证、或者该老实标"没验证"的信号。**

## 判据不满足时怎么办

**标"未通过 / 卡住"，然后回去补。** 不要让一份不合格的产出一边挂着"已完成"的状态，一边放着。

这条听起来像废话，但它是最常被违反的一条——因为"改状态"比"补验证"省事太多了。

## 一份合格的完成说明长什么样

```
【做了什么】
- 验证动作 1：{具体动作} → 结果：{实际看到什么}
- 验证动作 2：{具体动作} → 结果：{实际看到什么}

【关键假设】
- 假设：{最关键的 1~2 条}
  尝试推翻的方式：{成本最低的做法}
  结果：成立 / 被推翻 / 卡住

【没验证的部分】
- {哪些没验证、为什么、谁需要知道}
```

最后一节是硬要求。**任何"没验证的部分"都必须显式写出来**，不能因为尴尬就省略——它恰恰是最该让人知道的部分。

## 自检（交付前扫一遍）

- [ ] 我的完成判据是"动作 + 结果"，还是"东西已经在了"？
- [ ] 验证动作 ≥ 2 条，且没有"同上"？
- [ ] 关键假设有没有被**真的**试着推翻过？写了结果吗？
- [ ] 上面那五句蒙混话术，我说了哪句？
- [ ] "没验证的部分"写了吗？

## 边界

- 它管**"完成"这件事能不能被验证**，不管**验证得够不够深**——那是评审的尺度问题。
- 它**不适用于**探索性工作（调研、头脑风暴、试错）。那些事情本来就没有明确的终点，硬套判据只会变成形式主义。
- 它不能替你做验证。它的作用是把"我其实没验证"这件事**逼到台面上**——剩下的还得靠人去查。
