# blast-radius · 改动的爆炸半径

## 它解决什么

改一个**共享**的函数，修好了 A 现象，结果 B、C、D 三个地方跟着坏了。

或者更糟——你一口气改了五个地方。A 好了，B 坏了，但**你不知道是哪一处导致的**，只能一处一处试回去。

这两种情况的代价，比"多花半天"大得多：**你失去了判断能力。**

这个 skill 就一条铁律：

> **「最小改动」不等于「改得少」，而是「爆炸半径最小 + 能归因」。**

## 它纠正的三个常见理解

| 常见理解 | 正确的理解 |
|---|---|
| 最低成本 = 最少改几处、尽快把现象消掉 | 最低成本 = **相对已知良好基线**，影响范围最小、且**能单变量验证** |
| 分析时列了 ①②③④，那就可以一次全做 | 分析结果是**候选池**；真正落代码时，**一次只许动一条轴** |
| 这块偏了，那就间距、字体、容器一起调 | 在共享路径上，**加法优先于改法** |

## 六条硬规则

| # | 规则 | 一句话 |
|---|---|---|
| 1 | **先钉基线** | 找到"已知是好的那个版本"，默认停在它上面只做加法 |
| 2 | **一次只动一条轴** | 测量 / 布局 / 容器 / 字体 / 清洗，一次动一条——**打包会毁掉归因信息** |
| 3 | **加法优先于改法** | 先补前置条件 → 再调测量 → 才动布局 → 再动容器 → 最后动字体 |
| 4 | **"更严重"先回退** | 第一步是回退，不是在上面再叠一层 |
| 5 | **双约束验收** | 目标现象 + **守恒项**（本来对的地方不许坏）。缺守恒项不许动手 |
| 6 | **两个问题别打包** | 同一块上的两个问题，默认分开改 |

## 动手前必答的三个问题

1. **基线是什么？** 我凭什么认为它是好的？
2. **这次只动哪一条轴？** 其他轴为什么不动？
3. **如果对方说"更严重"，我回退到哪里？**

**第三个问题答不出来，说明你对这次改动没有控制力——那就先别动手。**

## 什么时候用它

- 要改的东西被**多处调用**（公共函数、公共组件、基础样式、工具类）
- 客户/测试反馈过"更新后更严重"
- 同一块代码上最近已经有过一次改动
- 现象很奇怪，你不确定改动会不会牵连别处

**只在"改共享代码"时用它。** 新功能从零搭建、或者改一个只被一处调用的私有函数，套这套规则纯属拖慢自己。

## 怎么简单测试（1 分钟）

重启工具，发这段（**故意给一个典型的"共享函数改动"**）：

```
用 blast-radius 帮我规划这个改动：

我们的公共工具函数 formatPrice() 现在返回的金额没有千分位，
我要给它加上千分位。这个函数在订单页、商品页、报表页都在用。
```

**通过标准**，它应该：

- 先问**基线**：现在这个函数的行为是什么？哪些地方依赖它？
- 要求写**守恒项**：加了千分位之后，那些**把这个字符串拿去解析/计算**的地方会不会坏？（这是最典型的"修好一个坏三个"）
- 建议**加法而不是改法**：能不能新增一个格式化函数，而不是直接改原来那个？
- 提醒**一次只动一条轴**：别顺手把小数位数、货币符号也一起改了
- 最后问一句：**如果上线后发现更严重，回退到哪里？**

**失败信号**：如果它直接给你一段改好的代码，说"这样改就行了"，那就是没装上。

## 设计取舍

| 选择 | 原因 |
|---|---|
| **把"最小"重新定义成"爆炸半径最小"** | "改得少"是个会骗人的标准——改一行公共函数可能比新加五十行更危险 |
| **一次只动一条轴会变慢，但坚持这么做** | 慢的代价是可控的，失去判断力的代价不可控 |
| **要求"守恒项"是硬性的** | 绝大多数事故都源于只验了"我修的那个"，没验"本来对的那个" |
| **强调加法优先** | 加法的副作用小，改法的副作用不可控。加个等待不会影响别的页面，改个间距可能影响十个 |
| **不适用于全新功能** | 没有"基线"和"守恒项"的场景，这套规则无从谈起 |

## 边界

- 它管**改动的安全性**，不管**方案对不对**——"这个需求该不该这么做"是另一回事
- 它**会拖慢速度，这是明确的取舍**。一次一轴意味着可能需要多轮。换回来的是：**每次出问题你都知道是哪一轴导致的**
- 它**拦不住你已经想做的大包改动**，只能提醒你拆开。拆不拆还是你自己的决定
