# blast-radius — 改动的爆炸半径

## 它解决什么

改一个**共享**的函数，修好了 A 现象，结果 B、C、D 三个地方跟着坏了。

或者更糟——你一口气改了五个地方。A 好了，B 坏了。但**你不知道是哪一处导致的**，只能一处一处试回去。

这两种情况的代价，远比"多花了半天"要大：你失去了**判断能力**。

## 一条铁律

**"最小改动"不等于"改得少"，而是"爆炸半径最小 + 能归因"。**

这三句话，每一句都在纠正一个常见误解：

| 常见理解 | 正确的理解 |
|---|---|
| 最低成本 = 最少改几处、尽快把现象消掉 | 最低成本 = **相对已知良好基线**，影响范围最小、且**能单变量验证** |
| 分析时列了 ①②③④，那就可以一次全做 | 分析结果是**候选池**；真正落代码时，**一次只许动一条轴** |
| 这块偏了，那就间距、字体、容器一起调 | 在共享路径上，**加法优先于改法** |

## 六条硬规则

### 1. 先钉住"基线"

找一个**已知是好的版本**（某个发布版本、某次提交、或者"上次还是正常"的那个时间点），把它当作基线 `B`。

**默认方案 = 停留在 `B` 的形态上，只做加法。** 不要在没排除清楚之前，把"改间距 + 改定位 + 换字体 + 改结构"打成一个包。

### 2. 一次只动一条轴

把可能的改动按性质分成几类轴，比如：

| 轴 | 动的是什么 |
|---|---|
| 测量 | 什么时候量、量几次、量多大 |
| 布局 | 间距 / 容器宽度 / 对齐方式 |
| 容器 | 渲染它的外壳（定位、可见性策略） |
| 字体 | 字体注入时机、字体替换 |
| 清洗 | 对内容的预处理（特殊符号、编码） |

**一次只动其中一条。** 要动第二条，先等第一条验证通过、单独交付。

理由前面说了：**打包会毁掉归因信息。**

### 3. 加法优先于改法

默认顺序，不许跳级：

```
先补前置条件（等资源就绪、等布局稳定）
  → 再调测量方式（量得更准/更大）
    → 才考虑动布局
      → 再考虑动容器
        → 最后才考虑动字体/结构
```

"直接改样式看起来更快" **不能**压过这个顺序——除非前面的手段已经被单变量验证证明无效。

原因是：**加法的副作用小，改法的副作用不可控。** 加一个等待不会有别的页面受影响，改一个 `margin` 可能让十个页面跟着变。

### 4. 说"更严重"了，第一步先回退

如果对方反馈"更新后更严重"，**第一步必须是回退或剔除最近在这块上的改动**，而不是在上面再叠一层。

回退稳定之后，再一条一条把"被证明需要的"加回来。

**不要在回归还没撤干净的时候，顺手去修另一个问题。**

### 5. 双约束验收（这条管"公共模块"）

凡是动到共享路径（被多处调用的函数、公共组件、基础样式），验收时必须同时写清**两条**：

| 约束 | 内容 |
|---|---|
| **目标现象** | 你要修的这个问题，修好了吗（原来坏的那个） |
| **守恒项** | 原来对的东西，还是对的吗（那些**不该变的**） |

**守恒项缺了 → 不许动手。** 这条是硬要求，因为共享路径上"修好一个坏三个"是常态，而绝大多数事故都是因为只验了目标、没验守恒。

守恒项怎么找：问一句 **"哪些地方也在用这个？它们现在是对的，我改了之后它们还对不对？"**

### 6. 两个问题一起改时，别打成一个包

如果同一块上同时有两个问题（比如"偏了"和"叠字了"），**默认不要放在一次改动里**。

列一个至少两行的对照表，写清各自的原因和排除理由，再决定是不是真的需要合并。

## 三个必答问题（动手前）

1. **基线是什么？** 我凭什么认为它是好的？我的改动怎么保证还停在这个形态上？
2. **这次只动哪一条轴？** 其他轴为什么不动？
3. **如果对方说"更严重"，我回退到哪一次提交、哪一段改动？**

第三个问题尤其重要——**答不出来，说明你对这次改动没有控制力**。那就先别动手。

## 最小改动四原则

| 原则 | 怎么做 |
|---|---|
| **简洁** | 补丁短。能抄现有同类做法就抄，不要重新发明 |
| **改动少** | 能"插一段"就不"改一段"。**禁止为了好看顺手抽公共层、顺手重构** |
| **逻辑清晰** | 新分支和旧分支**并列**写，不要嵌套进旧逻辑里 |
| **不影响旧逻辑** | 没有新数据就不进新分支；**把新分支删掉，旧路径应该一模一样** |

最后一条是最好用的自检：**把新加的部分删掉，行为是否和改动前一模一样？** 如果答案是"不一样"，说明你不只是"加了个东西"，而是**改动了原有逻辑**——那风险等级就完全变了。

## 先搜同类，再动手写

要加一个开关、单选、列表行、弹层这类**已经存在于你项目里的控件**时：

1. 先在**同一个项目、同一类页面**里搜索已有的实现
2. **能复用就复用**（连结构带样式一起抄）
3. 只有当需求确实要求新样式时，才新写——而且要说清**为什么不能复用**

理由和"基线"是一样的：**项目里已有的写法是已经验证过的**，你自己新造的一套是没验证过的。前者是零风险，后者是从零开始。

## 动手前的自检

- [ ] 我读过"改动前"的**真实代码**了吗（不是凭印象）？
- [ ] 基线 `B` 是什么？我的改动还停在它上面吗？
- [ ] 这次只动一条轴吗？动第二条了吗？
- [ ] 加法和改法，我选的是加法吗？
- [ ] **守恒项**写了吗？（哪些本来对的地方，不能被我的改动弄坏）
- [ ] 把新加的部分删掉，旧行为是否一模一样？
- [ ] 这块上还有别的问题吗？我是不是不小心打成包了？
- [ ] 如果对方说更严重，我回退到哪里？

## 边界

- 它管**改动的安全性**，不管**方案对不对**——"这个需求该不该这么做"是另一回事
- 它**不适用于新功能从零搭建**。没有"基线"和"守恒项"的场景，这些规则无从谈起
- **单行为轴会变慢，这是故意的。** 一次一轴意味着一次改动可能要多轮。它换回来的东西是：**每次出问题，你都知道是哪一轴导致的**。在小改动上这套可能显得啰嗦，但在共享路径上，它是唯一能保住判断力的做法
