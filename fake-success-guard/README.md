# fake-success-guard · LLM「假成功」检测

## 它解决什么

模型在没拿到你给它的输入时**不会报错**，它会顺着上下文编一个答案。HTTP 200 + 一段通顺的文字，完全可能什么都没干。

这类失败不抛异常，只会静默污染你的数据——等你发现时，已经错了几百条。

这个模块判断一次 LLM / 工具调用的返回，到底是**真拿到了结果**，还是**「假成功」**。

## 零依赖

Node 与浏览器通用，不需要安装任何东西。

## 用法

```js
const { check } = require('./fake-success-guard');

const r = check(modelOutput, { expect: [/型号/, /\d{7}/] });
if (!r.ok) {
  console.warn('假成功：', r.reason, r.detail);
  // 重试 / 换模型 / 标记为「不确定」，就是不要直接采信
}
```

`reason` 是刻意设计成可读的，方便你在日志里一眼看出失败在哪一步：

| reason | 含义 |
|---|---|
| `ok` | 通过 |
| `empty` | 返回为空 |
| `denial-input` | 模型明说没拿到输入（可信度最高，优先级也最高） |
| `denial` | 泛化的感知失败（说我识别不了） |
| `blind` | 短 + 反复说看不清 |
| `pleasantry` | 只有客套话，没有实质 |
| `missing-anchor` | 声明了要字段，却一个都没出现 |

## 怎么简单测试（10 秒）

```bash
node fake-success-guard/fake-success-guard.js
```

输出 `9/9 通过` 就正常。文件内置 9 条回归样本，**改任何规则之前先跑它**。

## 判定顺序很关键（别随手改）

```
1. 空返回
2. denial-input   ← 必须排在「锚点检查」之前
3. 锚点命中 → 通过
4. denial（泛化）
5. blind
6. pleasantry
7. missing-anchor
8. 通过
```

第 2 步不能挪到第 3 步后面。真实的失败输出长这样：

```
由于您未提供任何图像数据，我无法完成识别。型号：看不清，版本号：看不清。
```

它一边说没拿到图，一边顺手报了个字段名。**如果你的成功判据是「结果里有没有出现某个字段」，就会被它自己写下的谎话骗过去，直接放行。**

## 样本里为什么有两条「防误伤」

`SAMPLES` 里最后两条专门用来保证这套判定**不是一个脆弱的敏感词匹配**：

- 「该订单未提供手机号，因此无法发送短信通知」→ 应该判 `ok`，不能被「未提供」误杀
- 「识别结果如下：设备号 8661234。备注：右下方有一处无法识别的细小文字」→ 锚点已命中，应该判 `ok`

有这两条兜着，你才敢往规则里加词。

## 边界

**编得好的假答案会漏过。** 如果模型没收到图，却编了一段 400 字、格式完美、字段齐全的内容，这套规则挡不住。现在的护栏只能拦住「承认失败」和「明显敷衍」两类。

它是后验的文本特征判断，本质上是打补丁。如果你的做法能从调用链路上杜绝（让模型在任何情况下都无法返回「成功」而实际没拿到输入），那更好。
