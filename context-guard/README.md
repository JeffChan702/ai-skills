# context-guard · 长任务的上下文纪律

## 它解决什么

**上下文是工作台，不是硬盘。**

硬盘可以什么都存、永远都有空间。工作台不行——摊满了东西就没法干活了。AI 处理任务时的上下文就是这张台子，容量是固定的。

长任务失败，很多时候不是因为模型不够聪明，而是因为**台子被撑爆了**：一开始塞进几个大文件，中间又反复重读，最后台子上堆了几十万字，模型开始丢细节、答非所问，会话被强行中断，前面所有工作作废。

## 三条纪律

### 1. 大文件不整读

超过 50KB 的文件，别一次性整个读进来。正确顺序是：

```
先搜索定位（拿行号）→ 只读那一段（读 50 行，不是 5000 行）→ 立刻把要点写进一个文件
```

第三步最关键：**读到的内容如果不写下来，它就只存在于台子上**。台子一被清理，这些内容就没了，你还得再读一遍。

### 2. 会话被自动压缩后，不要凭记忆重读

长会话到一定长度会自动压缩——把前面的内容摘要成一段更短的文字，腾出台面。

**压缩之后，你对细节的记忆已经不可靠了。** 这时最容易犯的错是："这个文件我读过，但记不清了，再读一遍"——这一读，等于把刚腾出来的空间又填回去，而且**同样的内容读第二遍，收益是零**。

正确做法：**先读自己写的摘要文件**，缺哪块细节再按行号补读那一块。

### 3. 被压缩两次之后，先把结论写下来

如果已经遇到两次自动压缩、还要继续大范围读东西——**先停下来，把当前结论写进文件**。因为下一次压缩可能就把你刚想明白的东西丢掉了。

已经想清楚的事，**写下来才算真的留住了**。

## 会话是怎么死的（一次真实记录）

| 发生了什么 | 代价 |
|---|---|
| 一个 242KB 的页面 + 94KB 的脚本，被整篇读取 | 台子被占掉一大半 |
| 会话自动压缩，细节丢了 | 于是"再读一遍" |
| 重读、又压缩、又重读…… 来回 5 轮 | 反复填满，原地打转 |
| 中间还读了一张 505KB 的图片，读了 2 次 | 台子彻底满了 |
| **会话终止** | 这一轮全部工作作废 |

最讽刺的是：**那 5 轮重读，一次都没产生新信息。** 全是"我记不清了，再看一眼"——而看一眼的代价，是把刚腾出来的空间又用完。

## 什么时候用它

- 任务涉及多个大文件（日志、大页面、大脚本、数据文件）
- 会话已经跑了几十轮，你感觉 AI 开始"忘事"
- 处理图片（**图片别用文件读取工具读**——一张几百 KB 的截图转成文本有几十万字符，比任何代码文件都更容易撑爆台子）
- 你在做长链条的排查或重构

## 怎么装

把 `context-guard/SKILL.md` 复制到你的 skills 目录：

| 你在用的工具 | 目标路径 |
|---|---|
| Cursor | `~/.cursor/skills/context-guard/SKILL.md` |
| Claude Code | `~/.claude/skills/context-guard/SKILL.md` |
| WorkBuddy | `~/.workbuddy/skills/context-guard/SKILL.md` |

不需要装依赖。它是一份纪律约定。

## 怎么简单测试（30 秒）

重启工具，发这句：

```
用 context-guard 提醒我：接下来我要在项目里找「订单金额计算」的逻辑，
相关文件可能有几千行。说说你会怎么做。
```

**通过标准**：它应该说**先搜索关键词定位、只读相关行范围、把要点写进一个文件**。

**失败信号**：如果它说"我先把整个文件读一遍看看"，那就是没装上——那正是这个 skill 要防的事。

## 设计取舍

| 选择 | 原因 |
|---|---|
| **以 50KB 为界，而不是"看情况"** | 模糊的标准等于没有标准。有个具体数字，执行时才有判断依据 |
| **强调"写下来"而不是"记住"** | 整条纪律的支点就在这。压缩会丢记忆，文件不会 |
| **把"重读"当成头号敌人** | 大多数人以为风险是"读得不够"，其实长任务真正的杀手是"反复读同样的东西" |
| **不反对读文件** | 该读的还是要读。它反对的是**整篇读**和**重复读**，不是读本身 |

## 边界

- 它管**怎么用这张台子**，不管模型能力。台子管好了不会让它更聪明，但管不好会让它变笨
- 它**不适用于短任务**。十个文件、两轮对话的活，这些纪律纯属自我折腾
- 它**不保证会话不中断**。它只是把"会导致中断的行为"提前拦住——真正的上限还是由上下文容量决定
