# context-guard — 长任务的上下文纪律

## 它解决什么

**上下文是工作台，不是硬盘。**

硬盘可以什么都存、永远都有空间。工作台不行——摊满了东西，就没法干活了。AI 处理任务时的上下文就是这张台子，而它的容量是固定的。

长任务失败，很多时候不是因为模型不够聪明，而是因为**台子被撑爆了**：一开始塞进来几个大文件，中间又反复重读，最后台子上堆了几十万字，模型开始丢细节、答非所问，会话被强行中断，前面所有工作作废。

## 三条纪律

### 1. 大文件不整读

超过 50KB 的文件，**不要一次性整个读进来**。

正确做法：

```
先定位 → 再分段读 → 立刻记要点

1. 用关键词搜索拿到行号（不是读全文）
2. 按行号范围只读那一段（读 50 行，不是读 5000 行）
3. 把这 50 行里的要点，立刻写进一个 scratch 文件
```

第 3 步是关键。**读到的内容如果不写下来，它就只存在于台子上**——一旦台子被清理，这些内容就没了，你还得再读一遍。

### 2. 会话被压缩之后，不要凭记忆重读

长会话运行到一定长度，系统会自动做一次压缩：把前面的内容摘要成一段更短的文字，腾出台面空间。

**压缩之后，你对细节的记忆已经不可靠了。**

这时最容易犯的错，是"这个文件我读过了，但记不清了，我再读一遍"——这一读，等于把刚腾出来的空间又填回去，而且**同样的内容读第二遍，收益是零**。

正确做法：**先读自己写的 scratch 文件**。缺哪块细节，再按行号补读那一块。

### 3. 被压缩两次之后，先把结论写下来

如果你已经遇到两次自动压缩，而且还要继续大范围读东西——**先停一下，把当前结论写进文件**。

因为下一次压缩可能就把你刚想明白的东西丢掉了。

已经想清楚的事，**写下来才算真的留住了**。

## 会话是怎么死的（真实记录）

一次真实的翻车：

| 发生了什么 | 代价 |
|---|---|
| 一个 242KB 的页面文件 + 94KB 的脚本文件，被读取 | 台子被占掉一大半 |
| 会话自动压缩了一次，细节丢了 | 于是"再读一遍" |
| 重读，又压缩，又重读…… 来回 5 轮 | 台子反复被填满，每一轮都在原地打转 |
| 中间还读了一张 505KB 的图片，读了 2 次 | 台子彻底满了 |
| **会话终止** | 这一轮的全部工作作废 |

复盘下来最讽刺的是：**那 5 轮重读，一次都没有产生新信息。** 全是"我记不清了，再看一眼"——而看一眼的代价，是把刚腾出来的空间又用完了。

## 一张自查表

- [ ] 我有没有一次性读过超过 50KB 的文件？
- [ ] 读到的要点，我写进文件了吗？还是只在"脑子里"？
- [ ] 我是不是在重读一个我读过的文件？为什么？（如果答案是"记不清了"，先去读自己的摘要）
- [ ] 已经压缩过两次了吗？那先把结论写下来再继续。

## 顺带一条：图片别用文件读取工具去读

如果你们的工作里会处理图片，记住一条：**不要把图片直接丢进对话上下文**。

一张几百 KB 的截图，转成文本形式会有几十万字符——它比任何代码文件都更容易把台子撑爆。图片应该交给专门的识别工具处理，**只把识别出来的文字带回会话**。

## 边界

- 它管的是**怎么用这张台子**，不管模型能力——台子管好了不会让模型更聪明，但管不好会让它变笨
- 它不是"少读文件"。该读的还是要读，**它反对的是"重复读"和"整篇读"**
- 它**不适用于短任务**。如果任务本来就只有十个文件、两轮对话，这些纪律纯属自我折腾
