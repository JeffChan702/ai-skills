# requirement-anchor · 需求锚定 12 格

## 它解决什么

拿到一段需求（一份原型稿、一段描述、几张截图），最怕的是**理解偏了**：做了一半才发现"这个字段其实不用做""这个入口在另一个页面""这个删除到底是物理删还是逻辑删"。

这个 skill 用一张 12 格矩阵把需求边界锁死：

| | **增** | **删** | **查** | **改** |
|---|---|---|---|---|
| **产品层** | 业务上新增什么 | 业务上废弃什么 | 业务上查看什么 | 业务上修正什么 |
| **数据层** | 写哪张表 | 删哪条记录 | 查哪几张表 | 改哪些字段 |
| **展示层** | 入口与表单 | 入口与确认 | 列表与筛选 | 入口与可编辑项 |

每格必须写满四件事：**主句 + 证据 + 验收判定 + 可信度**。填不满，不许往下展开。

核心铁律只有一句：**任何需求 = 增删查改的变体。**

## 什么时候用它

- 拿到一份原型稿 / 设计稿 / 需求描述，要开始写技术方案之前
- 需求来自多个来源（文字 + 截图 + 会议口述），怕漏了什么
- 需求方说"就这么简单"，但你觉得边界不清楚
- 一行级的小修复——**也要填**，只填涉及的格子就行

## 怎么简单测试（1 分钟）

重启工具，发这段（故意留一个模糊点——"删除"，看它会不会问你）：

```
用 requirement-anchor 帮我锚定这个需求：

要做一个「商品标签管理」功能：
- 能新建标签，标签有名称和颜色
- 商品可以打多个标签
- 标签列表能搜索
- 管理员能删除标签

材料：只有我这段文字，没有原型稿。
```

**通过标准** —— 它应该表现出这几点：

- **12 格都填了**，其中"数据层-删"这类它无法从描述推断的格子，标 🔴 或 `[需补充设计]`，而**不是自己编一个表名**
- 每格都有 **验收判定**（比如"删除标签后，已打该标签的商品显示什么？"）——如果它只描述了功能、没给验收点，就是没做到位
- 输出里有**边界声明**（三层各一句）和**偏离检测**那句声明
- 对"管理员能删除标签"追问：是物理删还是逻辑删？删了以后已用该标签的商品怎么办？

**如果它一上来就给你一份"技术方案"，而不先填矩阵** —— 那就是没装上，或者你没说清用哪个 skill。

## 设计取舍

| 选择 | 原因 |
|---|---|
| **固定 12 格，不加不减** | 格子一多就没人填。三层（产品/数据/展示）× 四操作（增删查改）是刚好能把需求框住的粒度 |
| **每格必须有验收判定** | 这是整套方法里最值钱的一条。需求文档写"能删除标签"没用，写"删除后已打标签的商品列表同步刷新"才有用——后者能直接对照验收 |
| **三级可信度而不是"待确认"** | 把"不确定"拆成 🟡 可推断和 🔴 必须问人，能让实现阶段知道哪些可以先做、哪些必须先问 |
| **「—」合法** | 一个纯开关需求确实没有"删"。强行要求每格都有内容，会逼着人编东西出来 |
| **偏离检测声明** | 需求最大的敌人是范围蔓延。这句声明是回到原始边界的锚 |

## 边界

- 它**不判断需求合不合理**——那是评审的活，它只负责把需求的结构和不确定项摊开
- 对**纯口述、零材料**的需求帮助有限：那种情况该做的是先要材料（一份原型、几句原文），不是硬填
- 它不替代跟需求方的沟通。它只是把你的疑问**整理成一张能问出口的清单**
