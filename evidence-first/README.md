# evidence-first · AI 协作的证据纪律

## 它解决什么

AI 最危险的输出不是明显错误，而是**看起来合理的编造**。

它会给你的配置项起一个"符合命名习惯"的字段名，把新列"顺手插在列表末尾"，为了"防慢查询"多建几个索引，或者按教科书给你设计一张新表。每一条单看都合理——但它们**没有一条是基于你的实际情况得出的**。

这些决定会悄悄进入实现，最后变成「没人知道它是猜的」。等发现的时候，已经建在错误的前提上了。

这个 skill 就一条铁律：**任何没有依据的决定，都不许做。**

## 它具体管什么

| 情况 | 能不能做 | 怎么处理 |
|---|---|---|
| **有依据推断** | 可以做，继续 | 标注 `来源=推断（依据：xxx）`，进清单 |
| **无依据自定** | **禁止** | — |
| **穷尽检索后仍推不出、不定就卡住** | 允许**有限**自定 | 标 `来源=自定（待确认）` + 写明排除了什么，**置顶**告知人 |

它还配了一份**「禁止的合理化话术」**清单——一说出这些话，就说明你正在用"合理"替代"依据"：

> "这是常见的命名习惯" / "顺手插在末尾最方便" / "先造一个回头再改" / "先按标准做法建张新表" / "索引多建几个防慢查询"

## 反直觉的另一半：别烦人

这条纪律容易被误解成"什么都要问人"。恰恰相反——**确认开始后，不要为产品、命名、顺序这类问题反复征询用户**，那会把协作变成审讯。

正确节奏是：**自己按依据落定 → 写进自定清单 → 交付时一次性说清**（而且要写成人能懂的：拍板了什么、改在哪、没做什么）。

只有两种情况才该在开始问，且只问 1～2 项：缺关键材料开不了工，或者有看不懂的映射关系。

## 什么时候用它

- 让 AI 做**会落地到真实代码/配置/数据**的活（不是写文案、不是答疑）
- 需求材料不全，你担心它自己补全
- 团队多人用 AI，需要一个统一的"标注口径"
- 你被"它怎么擅自这么定了"坑过

## 怎么装

把 `evidence-first/SKILL.md` 复制到你的 skills 目录：

| 你在用的工具 | 目标路径 |
|---|---|
| Cursor | `~/.cursor/skills/evidence-first/SKILL.md` |
| Claude Code | `~/.claude/skills/evidence-first/SKILL.md` |
| WorkBuddy | `~/.workbuddy/skills/evidence-first/SKILL.md` |

不需要装依赖。它是一份纪律约定，本身不含脚本。

## 怎么简单测试（1 分钟）

重启工具，发这句（**故意什么都不给**，看它会不会直接开始编）：

```
用 evidence-first 帮我做这件事：

给用户表加一个「最后登录时间」字段，在列表页展示出来。
```

**通过标准**，它应该：

- **先指出自己缺什么**（字段叫什么名、放列表第几列、这个时间从哪来）——而不是直接甩一个 `last_login_time` 就开工
- 把能推断的和必须问你的**分开列**
- 输出一份**自定清单**，其中"必须人工确认"的项**置顶**
- **不会**反问你十个问题（那是走偏到另一边了）

**最容易看出来的失败信号**：如果它二话不说就给了你字段名、改文件列表、实现步骤，那就是没装上——或者它把这个 skill 当成了普通的代码生成指令。

## 设计取舍

| 选择 | 原因 |
|---|---|
| **三分类而不是"禁止猜"一刀切** | 绝对禁止会让 AI 卡死不动。分成"可推断/禁止/有限例外"才有可操作性 |
| **例外必须"穷尽检索"才可用** | 否则"我想不出来"会变成万能借口 |
| **要求标注来源，而不是只要求"别编"** | 光禁止没用。标注让编造**可见**——这是它真正能生效的原因 |
| **专门列"合理化话术"清单** | 编造从来不是明目张胆的，它总是穿着一件合理的外衣。把外衣一件件点破，人才认得出它 |
| **同时强调"别烦人"** | 只讲"要问"会走向另一个极端。纪律的完整形态是"该定的定、定完说清" |

## 边界

- 它管**决定有没有依据**，不管**依据够不够强**——"这个依据撑得起这个决定吗"是评审的事，不是它的
- 它**不适用于**写文案、答疑、头脑风暴这类没有"落地后果"的场景——那些场合放开让 AI 想，反而更好
- 它不保证 AI 一定遵守。它给的是**可检查的标注格式**，让你能在交付时一眼扫出哪些是推断、哪些是待确认
